# Схема для урока №2: Кодовый замок (CodeLock)

Вторая практическая схема для занятий по юнит-тестированию. Использует те же
компоненты, что и основной проект (**Keypad + LCD**), но добавляет понятную и
богатую на проверки **логику**, которую удобно покрывать тестами.

---

## 1. Идея

Кодовый замок: пользователь вводит PIN-код на клавиатуре.
- Верный код — замок открывается (загорается зелёный светодиод / щёлкает реле).
- Неверный код — счётчик ошибок растёт.
- После N ошибок подряд — замок блокируется (красный светодиод), ввод
  игнорируется, пока не сбросить.

Главный приём (тот же, что в `QuestionGen`): **логика отделена от железа**.
Класс `CodeLock` ничего не знает про Keypad и LCD — он лишь принимает символы
клавиш. Поэтому всю его логику можно протестировать на ПК.

```
  [Keypad] --символы--> [CodeLock (логика)] --состояние--> [LCD + светодиоды]
                              ^
                              |
                     это мы и тестируем
```

---

## 2. Схема подключения (Arduino Uno)

| Компонент | Подключение | Назначение |
|-----------|-------------|------------|
| Keypad 4x4 | строки → D2–D5, столбцы → D6–D9 | ввод цифр и клавиш `*` `#` |
| LCD I2C 16x2 | SDA → A4, SCL → A5, VCC → 5V, GND → GND | показ статуса и набора |
| Зелёный светодиод | D10 → резистор 220 Ом → светодиод → GND | «открыто» |
| Красный светодиод | D11 → резистор 220 Ом → светодиод → GND | «заблокировано» |
| (опционально) реле/серво | D12 | привод двери |

Раскладка клавиатуры:

```
1 2 3 A
4 5 6 B
7 8 9 C
* 0 # D
```
- `0`–`9` — ввод цифры
- `*` — стереть набор
- `#` — подтвердить код

## 3. Логика модуля `CodeLock`

Код модуля (в проекте): [`lib/CodeLock/CodeLock.h`](../../lib/CodeLock/CodeLock.h),
[`lib/CodeLock/CodeLock.cpp`](../../lib/CodeLock/CodeLock.cpp)

Публичный интерфейс:

| Метод | Что делает |
|-------|------------|
| `CodeLock(pin, maxAttempts=3)` | создать замок с кодом и лимитом попыток |
| `pressKey(char)` | обработать нажатие клавиши (`0-9`, `*`, `#`) |
| `isUnlocked()` | замок открыт? |
| `isLockedOut()` | замок заблокирован из-за ошибок? |
| `getFailedAttempts()` | сколько было неверных попыток |
| `currentEntry()` | что сейчас набрано (для вывода на LCD) |
| `reset()` | полный сброс состояния |

Правила поведения:
1. Верный код → `isUnlocked() == true`, счётчик ошибок обнуляется.
2. Неверный код → счётчик ошибок +1, набор очищается.
3. Достигли `maxAttempts` → `isLockedOut() == true`, ввод игнорируется.
4. `*` стирает текущий набор, `#` подтверждает.
5. Буфер набора защищён от переполнения.

## 4. Тесты

Тесты: [`test/test_codelock/test_codelock.cpp`](../../test/test_codelock/test_codelock.cpp)

Покрыто 9 случаев:

| Тест | Что проверяет |
|------|----------------|
| `test_correct_code_unlocks` | верный код открывает замок |
| `test_wrong_code_does_not_unlock` | неверный код не открывает, +1 ошибка |
| `test_star_clears_entry` | `*` стирает набор, можно исправиться |
| `test_lockout_after_max_attempts` | блокировка после N ошибок |
| `test_input_ignored_when_locked_out` | в блокировке ввод игнорируется |
| `test_reset_clears_state` | `reset()` снимает блокировку |
| `test_success_resets_failed_counter` | успех обнуляет счётчик ошибок |
| `test_overflow_is_safe` | длинный набор не ломает замок |
| `test_empty_submit_is_wrong` | `#` без ввода = неверный код |

Запуск:

```powershell
pio test -e native -f test_codelock     # только этот тест
pio test -e native                      # все тесты проекта
```

## 5. Задания для студентов

1. **Прочитать тесты.** Открыть `test_codelock.cpp`, разобрать, как «нажатия»
   через `pressKey()` имитируют работу с клавиатурой.
2. **Найти ошибку тестом.** В `CodeLock.cpp` временно убрать сброс счётчика при
   успехе (`failedAttempts = 0;`) — какой тест упадёт?
3. **Новое требование: тайм-аут вместо блокировки.** Предложить метод
   `unlockAfterTimeout()` и написать тест на него (по схеме AAA).
4. **Своя проверка.** Написать тест: после `reset()` метод `currentEntry()`
   возвращает пустую строку.
5. **Со звёздочкой.** Добавить смену PIN-кода (`changePin(old, new)`) — сначала
   тест, потом реализация (TDD).

## 6. Почему эту схему удобно тестировать

- Логика **детерминированная**: одинаковый ввод → одинаковый результат.
- Много **граничных случаев** (ровно лимит ошибок, пустой ввод, переполнение).
- **Нет зависимости от железа** в логике → тесты быстрые и не требуют платы.
- Хорошо показывает разделение «логика ↔ железо» — главный принцип
  тестируемого встраиваемого кода.

> Для сравнения: модули вроде `Display` (обёртка над LCD) тестировать смысла
> нет — там нет своей логики, только вызовы чужой библиотеки. Тестируем то,
> где есть **наши решения и правила**.
