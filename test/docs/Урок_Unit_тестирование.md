# Урок: Юнит-тестирование на PlatformIO (Arduino + Unity)

Практическое занятие: студенты научатся писать и запускать модульные тесты
для кода Arduino-проекта **на компьютере**, без загрузки на плату.

- **Тема:** модульное (unit) тестирование встраиваемого кода
- **Инструменты:** PlatformIO Core (CLI), фреймворк Unity, окружение `native`
- **Длительность:** ~90 минут (2 академических часа)
- **Проект для примера:** генератор примеров `QuestionGen` (модуль `lib/QuestionGen`)

---

## 1. Цели урока

После занятия студент умеет:

1. Объяснить, что такое юнит-тест и зачем он нужен.
2. Запустить тесты проекта одной командой.
3. Прочитать отчёт PlatformIO: где `PASSED`, где `FAILED`, сколько тестов прошло.
4. Написать собственный тест по схеме **AAA** (Arrange–Act–Assert).
5. Понять, почему код для микроконтроллера тестируют на ПК через «мок» железа.

---

## 2. Что понадобится (проверить ДО урока)

- Установленный **PlatformIO Core** (`pio --version` должен работать).
- Установленный **Python 3** (PlatformIO работает на нём).
- Проект `work_fc` склонирован/скопирован на каждый компьютер.
- Доступ в интернет на первом запуске (PlatformIO докачает фреймворк Unity).

> Сам микроконтроллер (Arduino Uno) на этом уроке **не нужен** — тесты идут на ПК.

## 3. Теория (10–15 минут)

### 3.1. Что такое юнит-тест
Маленькая программа, которая вызывает один «кусочек» нашего кода (функцию,
метод, класс) с известными входными данными и проверяет, что результат —
ожидаемый. Если результат не совпал — тест «падает» (FAILED) и сразу
показывает, где ошибка.

### 3.2. Зачем это нужно
- Ошибки находятся **рано**, до загрузки на плату.
- Можно смело менять код: тесты подскажут, если что-то сломалось.
- Тест — это ещё и **документация**: видно, как код должен себя вести.

### 3.3. Пирамида: ручная проверка vs автотесты
Проверять примеры «на глаз», загружая прошивку в плату, — долго и ненадёжно.
Автотест прогоняет **сотни** случаев за секунду.

### 3.4. Главная сложность встраиваемого кода
Код Arduino вызывает функции железа: `digitalRead()`, `analogRead()`,
`random()` и т.д. На обычном ПК их нет. Решение — **мок (mock)**: файл-заглушка,
который подменяет эти функции на ПК. В нашем проекте это
[`test/mocks/Arduino.h`](../test/mocks/Arduino.h) — он подменяет `random()`
и `randomSeed()`, которые использует `QuestionGen`.

## 4. Как устроен тест в проекте

Тесты лежат в папке `test/`. Каждый тест — в своей подпапке `test_*`:

```
test/
├── mocks/
│   └── Arduino.h              <- заглушка железа для ПК
└── test_questiongen/
    └── test_questiongen.cpp   <- сами тесты
```

В [`platformio.ini`](../platformio.ini) добавлено окружение для запуска на ПК:

```ini
[env:native]
platform = native            ; собирать под компьютер, а не под плату
test_framework = unity       ; фреймворк тестирования
build_flags = -I test/mocks  ; чтобы код нашёл заглушку Arduino.h
```

### Анатомия теста (схема AAA)

```cpp
void test_subtraction_non_negative(void) {
    QuestionGen gen(2, 10);                 // Arrange — подготовка
    for (int i = 0; i < 300; i++) {
        Question q = gen.next();            // Act — выполняем действие
        if (q.op == '-') {
            TEST_ASSERT_TRUE(q.answer >= 0);// Assert — проверяем результат
        }
    }
}
```

Главные макросы Unity:

| Макрос | Что проверяет |
|--------|----------------|
| `TEST_ASSERT_TRUE(x)` | что `x` истинно |
| `TEST_ASSERT_FALSE(x)` | что `x` ложно |
| `TEST_ASSERT_EQUAL_INT(a, b)` | что два целых равны |
| `TEST_ASSERT_FLOAT_WITHIN(d, a, b)` | что числа равны с точностью `d` |
| `TEST_FAIL_MESSAGE("текст")` | принудительно провалить с сообщением |

Каждый тест нужно зарегистрировать в `main()` через `RUN_TEST(...)`.

## 5. Запуск тестов (главная команда)

Из корня проекта (`C:\work_fc\test`):

```powershell
pio test -e native
```

Полезные варианты:

```powershell
pio test -e native -v                      # подробный вывод
pio test -e native -f test_questiongen     # только один тест
```

### Как читать отчёт

```
test_questiongen.cpp:79: test_answer_matches_operator   [PASSED]
...
============= 5 test cases: 5 succeeded =============
```

- `[PASSED]` — тест прошёл ✅
- `[FAILED]` — проверка не выполнилась ❌ (рядом будет файл и номер строки)
- `[IGNORED]` — тест пропущен
- Итоговая строка показывает общий счёт.

> Если видите `[PASSED]` у всех — это значит тесты **прошли**, а не пропущены.

| Время | Этап | Что делает преподаватель / студенты |
|-------|------|--------------------------------------|

## 7. Практические задания для студентов

### Задание 1 (базовое). Запустить и сломать
1. Запустите `pio test -e native` — убедитесь, что все 5 тестов проходят.
2. Откройте `lib/QuestionGen/QuestionGen.cpp`, временно «сломайте» логику
   (например, у сложения поставьте `q.answer = q.a - q.b;`).
3. Снова запустите тесты. Найдите, какой тест упал и на какой строке.
4. Верните код обратно — тесты снова зелёные.

> **Вывод для студента:** тест мгновенно ловит ошибку, которую на плате
> пришлось бы искать вручную.

### Задание 2 (основное). Написать свой тест
Добавьте в `test_questiongen.cpp` новый тест, проверяющий, что
**ответ на сложение никогда не отрицательный**:

```cpp
void test_addition_non_negative(void) {
    QuestionGen gen(2, 10);
    for (int i = 0; i < 200; i++) {
        Question q = gen.next();
        if (q.op == '+') {
            TEST_ASSERT_TRUE(q.answer >= 0);
        }
    }
}
```
Не забудьте добавить `RUN_TEST(test_addition_non_negative);` в `main()`.

### Задание 3 (со звёздочкой). Тест на новое требование
Допустим, появилось требование: **умножение не должно давать ответ больше 100**.
1. Напишите тест, который это проверяет.
2. Запустите — он, скорее всего, **упадёт** (при `10 * 10 = 100`... а при больших
   диапазонах и больше).
3. Обсудите: тест выявил, что требование в коде не реализовано. Это нормально —
   так работает подход «сначала тест, потом код» (TDD).

## 8. Частые проблемы и решения

| Проблема | Причина | Решение |
|----------|---------|---------|
| `pio: command not found` | PlatformIO нет в PATH | См. файл [`Настройка_PATH.md`](Настройка_PATH.md) |
| `Unknown environment names 'native'` | в `platformio.ini` нет `[env:native]` | Добавить окружение (см. раздел 4) |
| `fatal error: Arduino.h not found` | не подключён мок | проверить `build_flags = -I test/mocks` |
| Тест компилируется, но `FAILED` | это **не** ошибка сборки — это ошибка в коде/тесте | прочитать сообщение и номер строки |
| Долгая первая сборка | PlatformIO качает Unity | подождать, нужен интернет один раз |

---

## 9. Итоги урока (что записать студентам)

- Юнит-тест проверяет один кусочек кода автоматически.
- Команда запуска: `pio test -e native`.
- Тест строится по схеме **Arrange → Act → Assert**.
- Код для Arduino тестируют на ПК с помощью **мока** железа.
- `PASSED` = прошёл, `FAILED` = нашли ошибку (это польза, а не беда).
